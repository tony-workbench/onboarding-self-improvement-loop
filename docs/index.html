Onboarding self-improvement loop

An AI loop that finds where new users drop out of onboarding, proposes changes (big ones included), blocks anything that would delete a step or a job a screen does, reach outside onboarding or pressure users, A/B tests the rest, ships the winners, and rewrites its own lessons and scoring from denoised results. A round ends when its tests have results; the next round starts at once, on top of the improved version.

How one round works

Read the funnel and support themes through the data gateway
The model writes 10 ideas as onboarding config, asked to make at least 4 of them big moves
Code check, rule review and fairness review; any of them blocks
2 test slots go to big moves, then the best idea per funnel step, up to 5 tests
Test them at once on 50% of new users, 50/50, for one week; check every hour and stop any test that is clearly harmful
Ship every winner; re-test a winner first if its effect is mostly noise; roll back anything that clearly lowers finishing
Shrink results by their noise, rewrite lessons and rubric weights, start the next round

Steps 1 to 4 use real data and a real model (Gemini); step 7 is the same model learning from the simulated results. Step 5 uses simulated users because the app cannot yet switch onboarding per user; the code that would call Amplitude instead is in the repository. This is the same shape as AlphaEvolve: a generator proposes, a strict checker filters, a measured result decides what survives, and the result feeds the next round. The "self" part is that the loop also rewrites the lessons and weights it uses to choose.

Safeguards

The aim is not to stop the AI from making big changes; it is to make sure no change deletes part of the product, reaches outside onboarding, or treats users unfairly. Every limit below is enforced in code, outside the model, following OWASP's guidance on excessive agency (minimal tools, minimal permissions, authorization in code rather than in the model, logs of every action) and automatic rollback.

1. Big moves allowed, no step or job lost

Inside onboarding the model may redesign any screen, build screens from new components (animation, badge, button, checklist, choice_cards, image, mascot, name_input, photo_picker, preview, progress, sound, text, timer, tip_carousel, video), add up to 8 new screens or whole sub-flows (also after the home intro), move sign in later (after adoption, for example), and replace any part of a screen with something better. Code makes sure it cannot lose a step or a job: every existing screen (story, choose_path, sign_in, pick_friend, upload_photos, adoption_certificate, waiting, home_intro) stays, in its order; each part has a named job (story: intro_story; choose_path: path_options; sign_in: sign_in_options; pick_friend: pet_choices; upload_photos: photo_upload; adoption_certificate: certificate, official_stamp; waiting: wait_status; home_intro: home_welcome; every screen: settings_entry), and a replacement must use components that can really do it, with real content (a stamp needs a stamp asset, the path choice needs two distinct options for adopting and making your own, a sign-in button must say it signs in). Nothing on the sign-in screen may lead past it without signing in. Layouts and styles come from fixed lists, so nothing can be hidden. A change may only edit the screens of its own funnel step, and tests that run together never edit the same screen. Anything that names something outside onboarding, including new screens that look like payment, sign-up, account or settings screens, is rejected before any test exists.

2. Fair design

Regulators do not limit how much a product changes; they limit changes that deceive or pressure people. Code handles what code can check reliably: text is normalised (look-alike, full-width and invisible characters are rejected), links, addresses and markup are blocked, timers may only count a real wait, inputs may only ask for the pet's name, choices may not be age ranges, and a short list of phrases that are never fine (prices, skipping, pressure, shaming, personal questions) is blocked. Meaning is judged by a separate fairness review, a model call that reads every user-facing text and blocks anything that mentions money, suggests skipping, pressures, shames or asks about the person, however it is worded. Broad word lists were tried first: they both missed rewordings and blocked ordinary copy such as "feel free to look around". Because a pet app has young users, nothing may nudge children toward sharing more data (UK Age Appropriate Design Code, standard 13).

3. What the loop may do

Experiment calls go through one wrapper: create, start, stop, read, re-test and ship, only for tests this loop created, at most 5 running at once, traffic between 0 and the cap (checked against the number actually sent). Titles and descriptions sent to the platform are checked for links and markup. Other calls raise an error. Every hour, a test that is clearly worse on its step, the next step or finishing is switched off (see Harm limits).

4. What data it may read

Read-only, through a gateway that serves the onboarding funnel (onboarding events only) and the anonymized support themes. No user-level data, no raw mail, no keys: the model never holds a credential. Support themes reach the model marked as data, not instructions.

5. Base rules

A rule review, another model call that sees every full config, applies the company's rules; a change ships only if the code check, the rule review and the fairness review all pass it:

  • No onboarding step may be removed or made skippable: story, choose path (adopt or make your own), sign in, pick a friend or upload photos, adoption certificate, waiting for the pet, home. Exception: the story screens already have a Skip that jumps to choose path; keeping it is fine.
  • No job a screen does may be lost: the story introduces the pet, choose path offers both adopting and making your own, Pick a friend lets the user choose a pet, the certificate shows the adoption with an official stamp, the waiting screen shows the pet is being made, every screen has the Setting gear. Any design may be replaced by a better one, as long as it still does the same job.
  • Pricing stays as it is: the first adoption is free and later adoptions are paid. Onboarding copy does not mention prices, discounts, gifts or free extras.
  • Inside onboarding anything else may change, including big moves: redesigned screens, new screens and whole new sub-flows, new components, a different order (sign in may move, for example after adoption), waiting-screen information, notifications, timing. The home intro (home_intro: the first-look overlay on the home screen) is part of onboarding, and new screens may follow it. Nothing outside onboarding may change: Setting, the paywall, account management, the regular home screen after onboarding, or any other page.
  • Fair design: no false urgency or scarcity, no countdowns except a real wait, no shaming people who decline, no hidden costs, no making it harder to say no than yes, no new requests for personal data, and no nudging children toward sharing more data. (FTC dark-patterns report; EU DSA Art. 25; EU AI Act Art. 5; UK Age Appropriate Design Code, standard 13.)

21 safeguard tests check both sides: that big moves pass (a redesigned screen, a whole new sub-flow, sign in moved, the stamp or the pet picker replaced by something that does the same job) and that every way to delete, leave or pressure is blocked, including each bypass found by a red-team pass (look-alike characters, prices in words, hidden layouts, empty replacements, fake payment or sign-in screens, buttons past sign-in, hollow replacements, over-long configs, traffic outside the cap, tests left unclosed), plus 34 ordinary onboarding lines that must not be blocked. In the main run the audit log holds 135 entries; 24 are blocked attempts. The two model reviews are not guarantees and can be wrong in both directions; every block and its reason is listed in the round tables below.

Harm limits: what one bad test can cost Simulated

The safeguards above decide what a change may be. They do not limit what a permitted change does to the users who see it while it is tested: a fair, in-scope redesign can still make a step much harder. Before these limits, every test ran a full week and was judged once at the end, so a change that cut a step by a fifth hit every user in its group for seven days. A company deploying this needs a number for what one test can cost. Two parts give it, and a third is optional.

  • Hourly checks that stay valid however often they are read. Every hour each test is checked on its own step, the step after it, and finishing onboarding. The check is a mixture sequential probability ratio test, the method Amplitude Experiment uses by default, so reading it every hour does not raise the false-alarm rate; the 5% allowed over a whole test is shared by the three metrics. A test that is clearly worse on any of them is switched off at once, its users go back to the current version, and the experiment wrapper refuses to ship it. Amplitude does not switch a test off by itself, so the loop does it. This follows controlled rollout at Microsoft, Netflix's sequential canary tests, LaunchDarkly's guarded rollouts and Spotify's guardrail metrics.
  • A planned cost for every test. A big drop is caught within hours; a small one may never be proven within the week, but costs little per user. Before a test starts, the loop computes for every drop from 1% to 99%, on the test's own step, on the next step and further down (where only finishing overall sees it), and for every weekday the test could start on, how many finishers it would cost before the check stops it, and takes the largest. Each case is planned for an unlucky draw, so about 19 runs in 20 should cost less; it is a planned bound, not a guarantee. At 50% of new users it is 67 to 103 finishers per test, depending on the step, against about 1,069 finishers in a simulated week.
  • An optional weekly harm budget. The planned costs of all tests running in a week can be capped at a share of the week's finishers (RSI_HARM_BUDGET); a test that does not fit gets less traffic, down to a fifth of the usual share, or is skipped that round. Without a cap, the week is limited only by the 5 tests that may run at once, which together plan for 478 finishers (45% of a week's). The cap is off by default, because the comparison below shows what a 10% cap costs.

Stress test: planted harm and false alarms

Deliberately bad changes cannot be shown to real users, so the stress test runs in the simulator, with the real traffic shape: weekday shares and the day-to-day swings in the finish rate from eight real weeks of the daily report. Each test starts on a different one of those 56 days, with its weekday and its swing, so every weekend, quiet day and busy day is covered; a swing hits both groups of a test alike, as in a real test. 200 tests per cell, at 50% of new users.

The same loop with and without the checks

Learning with denoising, same seeds, run three ways: with the hourly check only (the default), with the check and a 10% weekly budget, and with one look at the end of each week. Finishers lost uses the simulator's hidden true effects, which a real deployment would not know; it is the number the checks exist to keep small. Finishers over the whole run counts every new user in the test rounds, at the version live that week plus what the tests added or cost, so a limit that slows improvement shows up there.

What we chose. The hourly check cuts the worst single test from 191 to 82 finishers on all new users (56 to 48 at half the traffic, where tests are smaller and slower to prove), and changes the end result by an amount within the run-to-run noise, so it is always on. The 10% weekly budget cuts the harm inside tests further, but on all new users over 20 weeks it ran 23% as many tests, saved about 517 finishers per run inside tests, and still ended about 10,536 finishers behind over the whole run, because improvement slowed. It stays available for a company that would rather improve more slowly than risk a bad week, set with RSI_HARM_BUDGET.

What this does not show

  • Users per hour are spread evenly over each day; real traffic has quiet nights and busy evenings, which slows the check at night.
  • Simulated users go through the whole funnel at once. Real users take minutes to days, so finishing counts lag and a real stop comes later than planned here. The check also needs funnel data every hour; the Amplitude code in this repository reads by day, and hourly reading has not been tried on the app.
  • Tests run at the same time share one slice of users and are watched one by one. Their combined effect, and the combined effect of winners shipped together, is not watched; it is assumed to be the sum of their single effects.
  • Harm here means fewer users reaching the next step or finishing. Harm that shows later (fewer users coming back in a week, more support mail) is not watched by the hourly check.
  • All of it is simulated. Before real traffic, an A/A test on the app (both groups see the current onboarding) should confirm that assignment, events and the check behave as here.

Choosing how many tests and how long Simulated

Five tests and one week are not guesses. We ran each setup for 12 simulated weeks, 600 times, on the ideas the model wrote, with true effects calibrated to published results (roughly a third of ideas help, a third make no measurable difference and a third hurt). One assumption is ours, not from a source: big moves are no better on average than small ones, but their effects spread twice as wide in both directions. Chosen setup: up to 5 tests at once, one per funnel step, all sharing 50% of new users; one full week each, one look at the end to decide a winner; ship every winner. (This study predates the hourly harm checks, which only ever stop tests early.) Exposure counts, per week on average, the share of new users sitting in a treatment that is actually worse (a user in several tests counts several times).

  • Share traffic, don't split it. Giving each test its own slice leaves each with too few users; it ships fewer winners and more false ones. Microsoft runs hundreds of overlapping tests for the same reason, isolating only tests that touch the same thing. Here that means one test per funnel step.
  • More tests at once is better, up to one per step.
  • Short tests, one look. One full week (the usual minimum, so weekdays and weekends both count) lets more ideas through in the same time. Checking every week without correcting the threshold raises false winners from 0.01 to 0.03 per run.
  • Ship every winner. Winners touch different steps, so they stack.
  • Traffic is the risk dial. 100% of new users finds more winners but exposes 2.0 times as many users to bad changes; 10% is safe but slow and more often fooled by noise. 50% with automatic rollback is the chosen middle.

These numbers come from the ideas of the published main run. With another run's ideas the size of each effect differs, and the order of close setups, such as one-week against two-week tests, can change.

How much could a better scorer add?

To tell a weak learning method from a simulator with little to learn, the same rounds were replayed offline with four ways of ordering the ideas that passed the safeguards in each saved learning run: a random order, the model's scores from that run, a scorer that knows the average effect of each kind of change on each step (what learning from past tests is meant to find), and one that knows each idea's true effect, luck included. Tests, shipping and the simulator are as in the loop, but without re-tests, the hourly check, the shared-screen rule or the harm budget, so the levels differ from the tables above; compare the rows with each other. Over 8 weeks the interval for it reaches 2.2 points, so a gain there is not shown but not ruled out. In this simulator most of an idea's effect is its own luck, which the simulator draws from the idea's title, not from its content, so there is little for learning from past tests to find. The model's scores did no better than a random order.

Three limits. The model's scores were given on the saved run's own path (its funnel, history and lessons) and are replayed on other paths here. With about 7 ideas a round that pass the safeguards, up to 5 tests and one per step, the rules leave a scorer little choice beyond which idea runs within each step, which also limits what any scorer can add. And the ideas themselves were proposed with learning on, so any effect of learning on what gets proposed is not measured here. The simulator therefore cannot show whether a model can judge an individual idea; real tests can. In a real deployment the loop would record every predicted effect and, after a few dozen tests, check whether its predictions beat a random order.

Denoising the learning signal

A one-week test on a few thousand users measures the true effect plus a lot of luck, and the winners are the ones that got lucky (the winner's curse). Learning straight from those numbers teaches the loop the luck. (In the 20-week batch above, learning from raw results still ended higher on average; the difference is within the noise.) Four published ideas are applied before anything is learned:

  • Shrink every measured effect toward zero by how noisy it is: corrected = τ² / (τ² + se²) × measured, where τ² is the spread of true effects around zero estimated from all tests so far (empirical Bayes, as in Deng et al., KDD 2021). The prior counts for more than our own history until about 100 tests, because the paper warns that 50 to 100 past experiments are needed for a stable estimate.
  • Weight results by reliability when averaging by kind of change, so noisy tests count for less (the reweighting idea in Wang et al., WSDM 2021, for noisy implicit feedback).
  • Re-test noisy winners: when shrinkage keeps less than half of a winner's measured effect, it runs one more week on fresh users while the next round starts. It ships if both weeks together, shrunk toward zero, are still clearly above zero and the fresh week points the same way; the loop learns from the fresh week alone, so choosing the winner and estimating its effect use different data. This is a shipping rule, so all three versions use it. Across all 50 re-tests in both batches, 43 held up and 7 were dropped, of which 7 were actually good changes. So in these runs the re-test cost some good changes without catching a bad one; its value would show only where more of the winners are false.
  • Require repeated evidence: a kind of change counts as a pattern only after two tests agree, and the model is asked to call a kind helpful only if a test of that kind actually won. This follows recent work on proactive assistants that learn a user's habits from repeated signals rather than single events (Shao et al., 2026).

Running it on Amplitude for real

AmplitudeExperiments in rsi/experiments.py has the same methods as the simulator:

  • Create: POST experiment.amplitude.com/api/1/experiments with control and treatment at 1:1, the change's config as the treatment payload, and a unique key per test.
  • Traffic and start: PATCH …/experiments/{id} with rolloutPercentage, then enabled: true.
  • Results: the onboarding funnel per group from the Dashboard REST API, split by the [Experiment] <key> user property; a re-test reads a separate date range of newly arrived users.
  • Ship: the treatment gets all traffic.

What the app needs first: at first launch, fetch the user's variant from Amplitude Experiment and build onboarding from that config. The keys stay in the service that runs the loop; the model never sees them. In this demo the loop advances the simulator one hour at a time; with Amplitude, an hourly job would read each test's funnel and switch off any test the check flags, which needs the hourly Dashboard REST API rather than the daily reads in this code. This part has not been run, so the calls, including the variant-weight change used to ship, should be checked against the current API first.

Data handling

  • Funnel: one week of the real funnel with generic event names; only rates and times between steps are published, no user counts. Simulated traffic uses an illustrative 6,000 new users a week.
  • Support mail: addresses, links, numbers and long IDs were stripped on the mail server; the stripped text was sent to the Gemini API, which rewrote every issue in its own words; a second model pass and a pattern check drop any line that still looks personal. The issues were then grouped by hand into themes, and anything raised by only one person was folded into a broader theme. No raw mail and no single-person issue is in this repository.
  • Traffic shape: eight weeks of daily onboarding starts and same-day finish rates, published only as indexes (each day divided by the eight-week average), with no user counts. The daily starts were counted two ways, daily unique users and daily cohort sizes, and matched on all 56 days.
  • Every model prompt and answer is saved in each run folder's cache/, so every run replays exactly without an API key.
